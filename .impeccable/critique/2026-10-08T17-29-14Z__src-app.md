## What to preserve

- The paper background, charcoal actions, sturdy typography, and restrained urgent red suit an operational tool. This does not need a rebrand.
- Workflow-aware actions, ownership, and related business/order/item context help people decide what to do next.
- Shared primitives already exist: `ListControls`, `BackLink`, avatars, contact links, status controls, confirmations, and toasts. The missing layer is shared page composition and behavior.

## Priority issues

### 1. [P1] Creation actions have no predictable home

Phone Book puts creation in the upper-right header. Pipeline combines its view switch with New intake in that header. Customer Service puts Log an issue below its status cards. Tasks has a quick-add input and a separate floating plus in the bottom-right corner.

The problem is not that Pipeline's button is on the right: that is a reasonable convention. The problem is that users cannot transfer that convention to other pages.

**Fix:** one shared page header: title and subtitle left; contextual creation action right. Put List/Board switching in the toolbar. Give Tasks a labeled New task action in the header and keep quick add as a secondary accelerator. Remove the competing floating creation pattern. Queues without an independent creation action do not need a fabricated New button.

Suggested commands: `$impeccable shape`, then `$impeccable layout`.

### 2. [P1] Lists reuse controls but not a common filtering experience

Phone Book has a sticky boxed toolbar containing search, counts, sorting/filtering and type chips. Pipeline boxes its list controls. Orders, Service and Tasks arrange controls and status filters in different regions. Tasks puts All/My tasks in yet another row.

There is behavioral inconsistency too: choosing a new field filter removes the previous field filter; some status/view links construct a fresh URL and discard other conditions. The generic label Default also hides the actual ordering. Different useful defaults are legitimate, but their meaning should be visible.

**Fix:** one toolbar immediately above results: Search → Filters → Sort → View switch. Show result count and active filter chips with individual removal and Clear all. Status, assignee and date should combine; switching List/Board should preserve applicable filters. Label the default sort meaningfully, such as Name A–Z or Oldest waiting.

**Consistency means identical mechanics and placement, not identical fields.** Phone Book needs contact search; Tasks needs owner and due date; Orders needs fulfillment status. Their data and row layouts can differ.

Suggested commands: `$impeccable shape`, `$impeccable clarify`.

### 3. [P1] Shared components need shared accessibility behavior

Small secondary text uses gray tokens with insufficient contrast for normal text: gray-dark is approximately 3.62:1 on white, and gray is 2.40:1. Task Priority is announced as Change status in the live accessibility tree. Task/Issue dialogs focus themselves and support Escape, but their source does not contain focus containment or restoration to the originating row; those keyboard behaviors were not fully exercised.

**Fix:** darker secondary text tokens, explicit accessible control names, and one accessible dialog primitive for focus containment, restoration, dismissal and scroll locking. This is another benefit of component reuse: fixes reach every view.

Evidence: [color tokens](</Users/nataliayurrita/Documents/ChatGPT/HSS Kitchens/hss-app/src/app/globals.css:23>), [Task dialog](</Users/nataliayurrita/Documents/ChatGPT/HSS Kitchens/hss-app/src/app/tasks/TaskModal.tsx:50>), [Priority control](</Users/nataliayurrita/Documents/ChatGPT/HSS Kitchens/hss-app/src/app/tasks/TaskModal.tsx:127>).

Suggested commands: `$impeccable audit`, `$impeccable harden`.

### 4. [P2] Record details have no common navigation and information contract

Company/Contact detail headers already resemble one another. Task/Issue modals also share a visual layout. Those are good partial patterns. Across the app, though, full pages, modals, tabbed details, Edit pages and immediate inline editing follow different conventions. Orders stacks progress, item status, overview metrics and editable metadata before its working tabs.

One confirmed navigation defect is more concrete than visual variation: selecting a specific service issue from a company detail opens generic `/service`, losing the selected issue.

**Fix:** every record opens a full detail page with a stable URL and a shared detail structure: Back/breadcrumb → title/status/actions → key metadata → related content → activity. Preserve the originating list's filters and scroll position. The user selected full detail pages for every record; reserve modals for short actions. Do not make every record display the same fields or tabs.

Evidence: [company issue link](</Users/nataliayurrita/Documents/ChatGPT/HSS Kitchens/hss-app/src/app/companies/[id]/page.tsx:314>), [Order header](</Users/nataliayurrita/Documents/ChatGPT/HSS Kitchens/hss-app/src/app/orders/[id]/page.tsx:327>), [Issue dialog](</Users/nataliayurrita/Documents/ChatGPT/HSS Kitchens/hss-app/src/app/service/IssueModal.tsx:83>).

Suggested commands: `$impeccable shape`, `$impeccable distill`.

### 5. [P2] Creating an issue displaces the service queue

Opening Log an issue expands a long inline form above the results. During the live inspection, later fields and submission required scrolling. A user handling a call loses sight of the queue and has to navigate the form's changing height.

**Fix:** launch a focused creation surface from the header, using the same creation pattern as other modules. Keep required capture first, reveal optional linking progressively, explain default assignment, and use a consistent Cancel/Log issue footer. Preserve unlinked issue logging so staff can capture a call before resolving all business details.

Evidence: [issue form](</Users/nataliayurrita/Documents/ChatGPT/HSS Kitchens/hss-app/src/app/service/LogIssueForm.tsx:264>).

Suggested commands: `$impeccable layout`, `$impeccable clarify`.

## Shared structure to adopt

| Shared component | Owns |
|---|---|
| PageHeader | Title, subtitle, contextual primary action, secondary actions. |
| CollectionToolbar | Search, filter state, sort labels, view switch, result count. |
| RecordList / RecordTable | Consistent row spacing, open affordance, loading and empty states; module-specific content. |
| DetailLayout / DetailHeader | Record identity, navigation, status, metadata and action order. |
| RecordRoute | Stable full-page record URL and preserved originating list context. |
| FormLayout / FormFooter | Field grouping, required indicators, errors, Cancel/Save placement. |
| Dialog | Accessible focus and dismissal behavior for confirmations and short interactions. |

The source already demonstrates why this matters: separate modules define near-identical PageHeader and DetailHeader helpers with different spacing/wrapping, while other pages build headers inline. Shared CSS cannot enforce a shared layout contract.

## Cognitive load and people affected

**Power users:** filtering status plus assignee can require rebuilding prior conditions; Tasks spreads ownership and creation across several zones.

**First-time users:** Company/Business, Deal/Opportunity and My Items/My tasks terminology makes related concepts look different. The quick-add input lacks a visible Enter instruction.

**Keyboard and screen-reader users:** misleading Priority labeling, pale text, and incomplete dialog focus handling undermine otherwise useful keyboard-open handlers.

The calm shell is reassuring. Switching modules creates the main friction: locating the same kind of action becomes work. Order's contextual next action is a strong moment, but competing summaries reduce its prominence. Phone Book shows eight type chips; Order shows a nine-phase stepper and five tabs. Group secondary choices instead of treating every destination as equally prominent.
