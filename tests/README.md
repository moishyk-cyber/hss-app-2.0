# Workflow regression checks

Run `npm test`. Tests call the same pricing, fulfillment, and attachment interfaces used by the server actions, with an isolated in-memory database adapter and storage adapter. No credentials, running application, or live records are needed.

The database adapter models transaction rollback and injects failures between related writes. These tests verify workflow outcomes and post-commit effects; they do not validate PostgreSQL's implementation of serializable isolation or the hosted storage metadata endpoint. Those dependencies remain Prisma/PostgreSQL and Supabase Storage in production.

Permissions and screen-specific audit descriptions remain in server actions. Shared reconciliation and fulfillment writes are transactional; audit entries and view refreshes happen after commit. Serialization conflicts retry up to twice without publishing effects from discarded attempts.

Deal values already entered are preserved. Order totals are recomputed only when all active items have prices. Optional intake attachments remain best effort, and direct uploads are cleaned up when Document recording fails. Signed uploads remain available after a failed recording so the same upload can be finalized again.

File pickers share a 20 MB PDF/image/Word (.docx) policy. Intake sends metadata through its server action, then uploads directly to storage after creating the record; attachment failures are shown with retry/open-record choices. `uploadFile.test.ts` exercises the client transport and attachment workflow together for intake, deal, order and purchase-order surfaces, using simulated storage and isolated records. It covers files above Next's default 1 MB action limit, validation, rejected/offline storage and finalization retry without resending bytes. Phone Book CSV parsing/import validation is covered by `phonebookCsv.test.ts`. Real Supabase upload/download checks require a configured `SUPABASE_SECRET_KEY` (or legacy `SUPABASE_SERVICE_ROLE_KEY`); these automated tests do not contact hosted storage.

Manual verification on 2026-10-15: native Chrome file selection passed for project intake (2 MB PDF), deal Files (PNG), order Files (2 MB PDF), purchase-order PDF (2 MB PDF), and Phone Book CSV import (one business and one linked contact). Real Supabase signed upload, metadata verification, Document creation and byte-for-byte download passed for orders, opportunities and purchase orders using the modern secret key. All temporary records, storage objects and the temporary sales test login were removed. CSV import now compares Origin with the public request host/protocol rather than Next’s internal URL; regression tests also verify that foreign origins remain rejected.

Default pricing assignment is configured in Admin → Settings. It starts unset and applies only to newly created quote/pricing line items, including intake; changing or clearing it never reassigns existing RFQ items. Explicit assignees and explicit unassignment take precedence. Inactive/deleted defaults are ignored, and deleting a teammate clears their default setting. `pricingAssignee.test.ts` covers these outcomes without changing live settings.

Closing responsibility follows each deal’s active salesperson, including historical closing steps on linked orders. Pipeline/dashboard ball-in-court badges advance from pricing using the same supplier-quote status criteria as the deal workflow; a stale New/Estimating stage does not block a completed intake and pricing handoff. `ballInCourt.test.ts` covers salesperson changes, missing/inactive owners, global-holder precedence, pending supplier quotes, removed items, intake evidence and won-order handoff.

Intake captures item details and quantity without amounts. Quote Received, Priced in AutoQuotes and Approved complete supplier-quote tracking even with no unit price. Quote price edits are rejected by the shared pricing workflow, which no longer initializes deal totals. The salesperson enters the required agreed total in Close; existing saved amounts remain preserved.

Purchase orders are logged using the required AutoQuotes PO number as both the primary PO number and AutoQuotes reference. Corrections update both together; the database unique constraint prevents logging a number twice. `purchaseOrders.test.ts` verifies exact number preservation, required input, corrections, transactional item assignment and serialization retries. Historical POs retain their saved numbers until corrected.

Each PO has an optional Expected Date, recorded with a date picker when logging or editing the PO. It is separate from item lead times and delivery dates. Regression tests cover create, correction, clearing and invalid dates. Apply `prisma/sql/20261015_po_expected_date.sql` before deploying this version.

Deliveries → Carriers & Truckers holds shared name lists. Choices include historical delivery names, and new names saved during scheduling are remembered transactionally for future use. Carrier/trucker fields on order acknowledgments and delivery details offer native searchable suggestions while allowing new names. Tests cover case-insensitive deduplication, separate lists and retaining a name after clearing a delivery assignment.

Delivered orders without open service issues leave the Orders kanban instead of automatically entering Customer Service. They remain in the table. Explicitly stuck work stays visible, and actual open service issues retain the Customer Service handoff. Completed/ready-to-complete orders open on Delivery instead of Service.

Service item Notes & updates are append-only authored entries, separate from technical activity and the resolution field. The server supplies the signed-in user and save date; failed writes leave the composer text available to retry. Tests cover attribution snapshots, issue isolation, validation and storage failures.
